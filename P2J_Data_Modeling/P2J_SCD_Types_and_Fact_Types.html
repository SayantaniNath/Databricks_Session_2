1. Is it a business process?

A business process is something the business does — a verb, captured by an operational system, happening at a point in time and producing numbers. Three tests:

TestQuestionVerdict
TimestampDoes it happen at a moment, or does it just exist?Happens → process. Just is → dimension.
MeasuresDoes the event produce numbers worth summing or counting?Yes → fact table.
GrainIs this a new grain, or the same row at a later time?Same grain later → milestone (a column), not a new table.

From a confirmed process you derive four things: the fact table (named after the event), the grain (one row per what), the measures (numbers the event produced), and the dimensions (the who/what/where/when hanging off it).

Carry rule: A new fact table needs a different grain, not a later timestamp.

2. The three fact table types

The discriminator is what causes a row to exist — not how often it happens.

TypeRows are born fromOne-question testAdditivity
TransactionAn eventNothing happened yesterday → no row for yesterdayFully additive
Periodic snapshotThe clock/calendarNothing happened yesterday → row anywaySemi-additive (sum across products ✅, across days ❌)
Accumulating snapshotA lifecycleOne row per thing, updated in place as milestones completeMilestone timestamps + lag measures
Misconception corrected 7/31: "anything that happens frequently is a transaction fact." Frequency is irrelevant. A stock-price snapshot taken every second is periodic; a contract renewal once a year is a transaction.

Worked example — inventory (the two-sibling case)

SKU-A has 500 on hand. Mar 1 a truck brings 200. Nothing Mar 2–5. Mar 6 a truck brings 50.

FactInventoryReceipt — transaction, 2 rows. Mar 2–5 do not exist in this table:

Mar 1 | SKU-A | WH-1 | 200
Mar 6 | SKU-A | WH-1 |  50

FactInventorySnapshot — periodic, 6 rows, one per day regardless:

Mar 1 | 700    Mar 4 | 700
Mar 2 | 700    Mar 5 | 700
Mar 3 | 700    Mar 6 | 750

Sum the receipt column across days = 250 received, meaningful. Sum the snapshot column across days = 4,250, meaningless. Only the calendar-driven table has the semi-additive problem.

The stock having a value is not the same as an event occurring. Apply the test to the table you are designing, not to the warehouse.

3. SCD Type 2 — the mechanism

Scenario. Priya covers Northeast. In March she transfers to West. Comp analytics needs every deal closed before March to still roll up under Northeast, and every deal after under West. Same employee ID.

You do not update her row. You close it and open a new one.

DimSalesRep — before:

rep_key | employee_id | region    | effective_from | effective_to | is_current
501     | E-8842      | Northeast | 2023-01-01     | 9999-12-31   | TRUE

After the 15 March transfer — two rows:

rep_key | employee_id | region    | effective_from | effective_to | is_current
501     | E-8842      | Northeast | 2023-01-01     | 2026-03-14   | FALSE
502     | E-8842      | West      | 2026-03-15     | 9999-12-31   | TRUE
ColumnJob it does
rep_keySurrogate key — a new one per version. This is what makes the design work.
employee_idNatural/business key — identical on both rows. It's what says "these two rows are one person."
effective_from / effective_toThe window in which this version was true. Open-ended row carries 9999-12-31.
is_currentFlag ETL uses to find the live row quickly.

Optional additions: version_number, row_hash (for change detection), audit timestamps.

What the ETL does on the change date

  1. Detect the change (row hash or column compare against the current row).
  2. UPDATE the old row: set effective_to = change date, is_current = FALSE.
  3. INSERT a new row with a new surrogate key, effective_from = change date, effective_to = 9999-12-31, is_current = TRUE.

Update-then-insert. Never overwrite the attribute in place.

The payoff — why it's automatic

A January deal stored rep_key = 501 on the fact; an April deal stores 502. Comp analytics simply joins fact → dim on the surrogate key and history comes out correct — no date logic, and no filtering on is_current. The fact froze the correct version at load time.

Diagnostic to remember: if a historical report has to filter is_current to produce the right number, something upstream is already broken — most likely the fact stored the natural key instead of the surrogate key.

Fact-side lookup rules

  • Normal load: look up the dimension on the natural key where is_current = TRUE, store that surrogate key on the fact.
  • Late-arriving fact: look up instead with event_date BETWEEN effective_from AND effective_to. Range joins belong in ETL backfill/repair — not in consumer queries.

4. Type 1 vs Type 2 vs Type 3

TypeWhat it doesUse when
Type 1Overwrite in place; history lostThe old value was simply wrong (a correction), or nobody analyzes by the attribute
Type 2New row per version; full history keptThe old value was right at the time and past facts must still roll up to it
Type 3prior_value column on the same row; one step of historyOnly the immediately previous value is needed, side by side with current

Discriminator to say out loud in an interview: "Is the old value wrong, or was it right at the time?" Wrong → Type 1. Right at the time → Type 2.

6. Interview quick-fire

QuestionAnswer in one breath
How do you preserve history on a changing dimension attribute?SCD Type 2 — close the old row (effective_to, is_current=FALSE), insert a new row with a new surrogate key; natural key unchanged.
What ties the two rows together?The natural/business key. The surrogate key is what makes them different.
How does a report get historically correct numbers?The fact stored the surrogate key current at event time — plain join, no date logic, no is_current filter.
Transaction vs periodic snapshot?If nothing happened yesterday: no row → transaction; row anyway → periodic.
When is Type 2 the wrong answer?Attribute nobody groups by (Type 1); attribute churning faster than facts arrive (mini-dimension / Type 4); only one prior value needed (Type 3); source has no reliable change detection.
Four delivery-stage timestamps — one table or four?One. Accumulating snapshot, same grain, updated in place. A new fact table needs a different grain, not a later timestamp.
