Story 1 — Consumption Layer Consolidation (Citi)

ScopeInfluenceLeadershipStrong metrics

Context

At Citibank, four business domains were each running their own separate Oracle pipeline into Tableau for the same category of reporting — same underlying source data, four different schemas, four teams doing redundant work to maintain it.

Scope

Four business domains, dashboards used by 200+ business stakeholders, tables in the half-million-to-million-row range each.

Action

I designed one shared consumption layer to replace the four separate pipelines — a single data model, the right indexing, and views built around how people actually queried the dashboards. I led the migration myself and ran the new model in parallel with the old ones so nobody's reporting broke during the switch.

Challenge

The hard part wasn't the design — it was that four teams already depended on the old pipelines daily. I had to prove the new model matched the old numbers exactly, table by table, before anyone would agree to retire the legacy ones.

Influence

Once live, ten-plus engineering teams adopted the same pattern for new domains — it stopped being "my project" and became the reference architecture.

Leadership

I mentored three junior engineers and vendor resources through the migration — schema walkthroughs, code reviews — so the pattern would hold up without me in the room.

Metrics

Source-to-mart latency dropped 40%, Tableau query performance improved 45%, now serves 200+ users org-wide.

Follow-up bank

Likely questionHonest answer
How did you measure the 40%/45%?BI/reporting team tracked it via Tableau query performance metrics and Oracle execution stats, before vs. after consolidation.
Your call or your manager's?I proposed and owned the architecture; got sign-off given the cross-team blast radius, but the design decisions were mine.
Any pushback from the four domain teams?Yes — migration risk concerns. Addressed with parallel-run + phased cutover, proving equivalence before cutting over.
What would you do differently?Get stakeholder buy-in earlier in the design phase; automate the parallel-run verification instead of checking manually.
Hardest technical decision?Reconciling four divergent schemas into one model without breaking anyone's existing dashboard filters.

Do not mention Kafka, GraphQL, or Redis in this story — none were real here. If asked "what was the tech stack," say plainly: Oracle, light Talend ETL, SQL, and dimensional modeling.

Story 2 — Healthcare Data Architecture: IQVIA → ClinicalFlow → Snowflake

ScopeGlobal/AmbiguityLeadershipPersonal-project continuity

Context

At IQVIA–Bayer, I designed the global healthcare analytics data model — standardized across 15+ clinical programmes worldwide, each with HIPAA and GDPR requirements to satisfy simultaneously.

Scope

Not one dataset — a repeatable architecture pattern deployed across 15+ programmes globally, each with its own source ERP systems and regulatory environment.

Action

I chose Data Vault 2.0 — hubs, links, satellites — over a flat Kimball model, specifically because the source ERP schemas were volatile across programmes; Data Vault absorbed that volatility without breaking downstream reporting every time a source changed. I layered Kimball-style marts on top for the actual BI consumption.

Challenge

The hard part was building one pattern that had to work across 15+ different regulatory and technical environments at once — not a single deployment, something other teams could repeat independently.

Leadership / Influence

The pattern was adopted and standardized across all 15+ programmes globally, becoming the reference model for how the org handled healthcare data compliance.

Continuity — personal deepening (label this explicitly as personal)

Since then, I've kept building in this same domain on my own time. I built AWS ClinicalFlow — a healthcare data lakehouse using Synthea synthetic EHR data: S3 with KMS encryption, Glue and EMR for HIPAA Safe Harbor de-identification and readmission analytics, Iceberg tables, and a Redshift gold layer with column-level privileges for the BI-facing views. I've also done hands-on Snowflake work — building queries and views — to round out my warehouse experience beyond Redshift. I'm upfront that ClinicalFlow is a personal project, not production work — but it's the same healthcare-data problem I owned professionally at IQVIA, just with the modern cloud-native stack.

Follow-up bank

Likely questionHonest answer
Why Data Vault over Kimball there?Source ERP schema volatility across programmes — needed something that absorbed change without breaking every downstream report.
Is ClinicalFlow professional or personal?Explicitly personal/learning project. Same domain (healthcare, HIPAA/GDPR) as IQVIA, but modern stack (S3/Glue/EMR/Iceberg/Redshift), built to deepen architecture skills beyond the Oracle-era tooling I used in production.
What's your real Snowflake depth?Hands-on building queries and views — not architecture-level ownership. Redshift is where I have more depth, via ClinicalFlow's gold layer.
Any compliance specifics?HIPAA Safe Harbor de-identification (tokenization, age-bucketing, zip-prefix truncation, SSN nulling) and GDPR erasure via a dedicated consent dimension — real production pattern at IQVIA, same pattern rebuilt hands-on in ClinicalFlow.

Don't blend ClinicalFlow's Redshift/Iceberg work into the IQVIA story as if it were the same engagement — always separate "what I owned in production" from "what I built myself afterward to go deeper."

How to use this doc

  • Pick whichever story matches what's asked: Story 1 for architecture/optimization/ownership questions, Story 2 for global scope/compliance/leadership-under-ambiguity questions.
  • Say each one out loud, unscripted, until the beats come out consistently — memorizing exact words sounds robotic; knowing the beats (Context → Scope → Action → Challenge → Influence → Leadership → Metrics) keeps it natural under follow-up pressure.
  • Never let a follow-up push you into inflating scope or tech stack beyond what's in the "honest answer" column above.
