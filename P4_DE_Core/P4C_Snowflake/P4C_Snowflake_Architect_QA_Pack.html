1. The architecture — the question behind every other question

Q: Explain Snowflake's architecture.

Three physically separate layers — this separation is the answer to almost everything else:

  1. Cloud services — the brain. Authentication, metadata, the optimizer, transaction management, access control, the result cache. You don't size it, you don't pay for it directly (mostly).
  2. Compute — "virtual warehouses." Independent MPP clusters. Multiple warehouses read the same data with zero contention. This is the bit you size and pay for by the second.
  3. Storage — data in cloud object storage (S3/GCS/Blob), in Snowflake's compressed columnar format, organised into micro-partitions. Cheap, and completely decoupled from compute.
Why this matters, said as an architect: "Because storage and compute are separated, I can give the BI team a Small warehouse and the data-science team an X-Large on the same tables, and neither slows the other down. Scaling for concurrency and scaling for query size become two different decisions instead of one — that's the thing you can't do on a classic MPP appliance like the Redshift or Teradata generation."

2. Virtual warehouses — sizing, scaling, cost

Q: How do you size a warehouse?

  • Sizes step XS → S → M → L → XL …, each doubling compute and cost per hour. XS = 1 credit/hr, S = 2, M = 4, L = 8, XL = 16.
  • Doubling the size roughly halves the runtime for a large scan — so cost is often flat while latency improves. That's the key insight: going bigger is frequently free in credit terms for big queries, and pure waste for small ones.
  • Small queries don't benefit at all — you pay 2× for the same runtime.
  • Method: start at XS, scale up until runtime stops improving proportionally, stop there.

Q: Scale UP vs scale OUT?

Scale up (bigger size)Scale out (multi-cluster)
FixesOne slow queryMany concurrent queries queuing
MechanismMore compute per clusterMore clusters, auto-added under load
ConfigWAREHOUSE_SIZEMIN_CLUSTER_COUNT / MAX_CLUSTER_COUNT, plus SCALING_POLICY (Standard = favour speed, Economy = favour credit savings)

The diagnostic: queries queuing → scale out. A single query slow with no queue → scale up.

Q: How do you control cost?

  • AUTO_SUSPEND (60s is a sane default) and AUTO_RESUME. Idle warehouses are the classic bill leak.
  • Resource monitors — credit quotas with notify/suspend actions at thresholds.
  • Separate warehouses per workload so you can attribute spend, not just observe it.
  • Right-size down as well as up; review WAREHOUSE_METERING_HISTORY.
  • Kill the long-tail: STATEMENT_TIMEOUT_IN_SECONDS.

3. Micro-partitions and clustering — the performance question

Q: What is a micro-partition?

Snowflake automatically divides table data into micro-partitions of ~50–500 MB uncompressed, stored columnar. For each one it keeps metadata: min/max per column, distinct counts, nulls. You never create or manage them.

Q: So how does pruning work?

The optimizer reads the min/max metadata before touching data and skips any micro-partition that can't contain matching rows. A filter on a column that correlates with load order prunes beautifully; a filter on a randomly-distributed column prunes almost nothing.

Q: When would you add a clustering key?

Default answer: usually you wouldn't. That's the senior answer. Natural load order already clusters by time, which matches most filters. Clustering keys cost continuous background credits (automatic reclustering).

Add one when: the table is large (multi-TB), queries filter on something other than load order, you've confirmed poor pruning via SYSTEM$CLUSTERING_INFORMATION, and query volume justifies the reclustering spend. Pick low-to-medium cardinality columns, most-filtered first — clustering on a unique id is the classic mistake.

4. Time Travel, Fail-safe, cloning

FeatureWhat it isRetention
Time TravelQuery/restore data as of a past point — AT(TIMESTAMP => …), BEFORE(STATEMENT => …), UNDROP1 day default; up to 90 days on Enterprise+
Fail-safeSnowflake-operated disaster recovery after Time Travel expires. You cannot query it — you file a support requestFixed 7 days, non-configurable
Zero-copy cloneNew object sharing the same micro-partitions; storage charged only on divergenceInstant, effectively free at creation

The architect angle: longer Time Travel means more storage cost, because changed micro-partitions are retained. It's a governance decision, not a default — set it per table by criticality. Clone production into dev for realistic testing at near-zero cost; that's the standard answer to "how do you get prod-like test data without copying a petabyte?"

vs Delta: Time Travel ≈ Delta's log-based versioning (but Delta's is bounded by VACUUM); zero-copy clone ≈ SHALLOW CLONE. Fail-safe has no Delta equivalent.

5. Ingestion — and the Ōura-relevant comparison

MethodUse when
COPY INTOScheduled bulk loads. You control the compute and the batch.
SnowpipeContinuous micro-batch, event-triggered on file arrival. Serverless — you don't run a warehouse. Latency ~1 minute.
Snowpipe StreamingRow-level streaming ingestion, seconds of latency, no files at all. This is what you'd pair with Kafka.
External tables / Iceberg tablesQuery data in place on S3 without ingesting. Iceberg tables give you open-format storage with Snowflake as the engine.

Snowpipe vs Auto Loader (she knows Auto Loader cold from 2G): both are incremental file ingestion with exactly-once semantics. Snowpipe is serverless and event-driven with no cluster to run; Auto Loader is a Structured Streaming source that you host, with richer schema-evolution control via schemaEvolutionMode and _rescued_data. Snowpipe's schema handling is far more rigid.

Streams and Tasks = CDC

  • A Stream is a change-tracking object over a table — it records inserts/updates/deletes since you last consumed it. Offset advances when consumed inside a DML statement.
  • A Task is scheduled SQL, chainable into DAGs, with WHEN SYSTEM$STREAM_HAS_DATA() to skip empty runs.
  • Together: Stream + Task + MERGE = incremental pipeline. This is Snowflake's answer to Delta Change Data Feed.

Tasks vs Airflow: Tasks are in-database, no infrastructure, but limited to Snowflake and weak on cross-system dependencies and observability. Airflow orchestrates across systems with real lineage and alerting. Use Tasks for tight in-warehouse loops, Airflow when the pipeline crosses boundaries — which for a data-mesh architecture it always does.

7. Caching — three layers, know which is which

  1. Result cache (cloud services) — identical query, unchanged data, 24 hours. Returns with no warehouse running at all, costs nothing. This is why a repeated dashboard query is instant and free.
  2. Local disk / warehouse cache (SSD on the compute nodes) — data read from storage stays warm. Lost when the warehouse suspends — which is the real trade-off behind aggressive AUTO_SUSPEND.
  3. Metadata cache — min/max stats; makes COUNT(*) and MIN/MAX answerable without scanning.
Common follow-up: "Why did the same query take 40s then 0.2s then 8s?" → first run cold; second hit the result cache; third ran after a DML invalidated the result cache but the warehouse was still warm, so it used local disk cache.

8. Semi-structured, sharing, and the rest

  • VARIANT — native semi-structured column (JSON/Avro/Parquet/XML). Access with col:path.to.field::type. LATERAL FLATTEN explodes arrays into rows. Snowflake shreds VARIANT into columnar sub-columns internally, so it's genuinely performant — but define explicit columns for anything queried constantly.
  • Secure Data Sharing — share live data with another account with no copy and no ETL; consumer pays their own compute. Cross-region/cross-cloud needs replication. Analogous to Delta Sharing.
  • Editions matter in interviews: Standard has no masking/row policies; Enterprise adds them plus 90-day Time Travel and multi-cluster; Business Critical adds HIPAA/PCI compliance support and customer-managed keys. For a health company like Ōura, Business Critical is the relevant tier — say that, it shows you think about compliance as an architecture constraint.
  • Iceberg tables — Snowflake as compute over open Iceberg tables on your own S3. The trade: no lock-in and multi-engine access, versus giving up some native performance features and owning table maintenance yourself.

9. The experiments that convert this from recall to experience

Two hours, free storage, and they make ~40% of the answers above yours. Do these before any Ōura technical.

Setup: Snowflake trial → set a resource monitor → use SNOWFLAKE_SAMPLE_DATA.TPCH_SF1000 (free, shared, storage costs nothing).

Experiment A — warehouse sizing curve

-- run the SAME aggregate on XS, S, M, L
ALTER WAREHOUSE lab SET WAREHOUSE_SIZE = 'XSMALL';
ALTER SESSION SET USE_CACHED_RESULT = FALSE;   -- else you measure the cache

SELECT l_returnflag, l_linestatus, SUM(l_quantity), AVG(l_discount), COUNT(*)
FROM SNOWFLAKE_SAMPLE_DATA.TPCH_SF1000.LINEITEM
GROUP BY 1,2;

-- then check what it cost and scanned:
SELECT query_text, warehouse_size, execution_time/1000 AS secs,
       bytes_scanned, partitions_scanned, partitions_total
FROM SNOWFLAKE.ACCOUNT_USAGE.QUERY_HISTORY
ORDER BY start_time DESC LIMIT 10;

Record: runtime per size, and where the halving stops. That gives her a sentence no other candidate has: "On a 6-billion-row table the curve flattened after ___, so going beyond that was paying double for nothing."

Experiment B — pruning

Run one query filtered on l_shipdate (correlates with load order) and one filtered on a scattered column. Compare partitions_scanned / partitions_total in QUERY_HISTORY. That ratio is pruning, and quoting a real one is the difference between explaining micro-partitions and having observed them.

Experiment C — the caching sequence

Run a query cold → rerun identical (result cache, ~0.1s, no warehouse) → change one literal (local disk cache) → suspend the warehouse, rerun (cold again). Four numbers, and §7 becomes something she watched happen.
