Pillar 4A — Kafka: Core Concepts

Sessions: 2026-07-27, 2026-07-29, 2026-07-30 (full re-teach from scratch). Covers: the log, partitions, brokers, replication, partitioning strategy, exactly-once, plus a 2D Structured Streaming checkpoint recap.

1. Why Kafka exists

6 producers × 8 consumers point-to-point = ~48 integrations. Kafka in the middle = 14 connections. It is a decoupling buffer — not a database, not a classic queue.

The log

A topic is an append-only, immutable, ordered sequence of records. Writes only append. Positions are offsets.

topic "rides"
[0][1][2][3][4][5][6]  → new writes append here

Two consequences that separate Kafka from RabbitMQ/SQS:

  1. Reading does not delete. Many consumer groups read the same topic independently; a new team can replay from offset 0.
  2. Retention is time/size based, not consumption based. Default 7 days. Consumer down 9 days = permanent loss.

Partitions

topic "rides"
  partition 0: [0][1][2][3]
  partition 1: [0][1][2]
  partition 2: [0][1][2][3][4]
Offsets are unique only within a partition, never across the topic.
Ordering is guaranteed within a partition, never across a topic.
A partition is read by at most one consumer per group → partition count is the parallelism ceiling.

Q: 6 partitions, 10 consumers in one group? 6 consume (one partition each), 4 sit idle as hot standbys — if one dies a rebalance hands its partition over in seconds.

2. Brokers and the cluster

A broker = one Kafka server. A cluster = several brokers. Partitions spread across brokers = horizontal scaling.

topic "rides", 6 partitions, 3 brokers
Broker 1: p0, p1    Broker 2: p2, p3    Broker 3: p4, p5

bootstrap.servers is only a phone book — the client fetches metadata, then talks directly to the leader broker. No proxy in the path. 2–3 addresses suffice for a 50-broker cluster.

ZooKeeper → KRaft. Kafka 3.x+ uses its own Raft implementation; metadata lives in an internal Kafka topic. Simpler ops, faster failover, far higher partition counts.

Why Kafka is fast

  • Sequential disk I/O — appending to the end of a file; no random reads/writes, no per-message index.
  • Zero-copy — sendfile() pushes bytes from page cache straight to the socket, never through the JVM heap. Hence small heap, big page cache.

On disk: a partition is a directory of segment files (~1 GB). Retention deletes whole segments, not individual records — which is why data can outlive its retention setting slightly.

3. Replication and durability

Every partition has N copies (replication.factor, normally 3): one leader, the rest followers.

p0 → Broker 1 (LEADER) | Broker 2 (follower) | Broker 3 (follower)
p1 → Broker 2 (LEADER) | Broker 3 (follower) | Broker 1 (follower)
Followers serve no client traffic. They are not read replicas — they exist only to take over. All reads and writes for a partition go to its leader. Leadership is spread so every broker does real work.

Replicas are always on distinct brokers (RF=3 needs ≥3 brokers). With broker.rack set, replicas spread across AZs — an entire AZ can fail and the partition survives. Cost: cross-AZ traffic charges + added acks=all latency.

Note: a partition lives on one broker; a broker may have many disks (log.dirs). Different partitions sit on different disks; one partition's log is on exactly one disk.

ISR — In-Sync Replicas

Replicas caught up with the leader (within replica.lag.time.max.ms, default 30s). Laggards are ejected and rejoin when caught up. Only an ISR member can be elected leader.

acks — the durability dial

acksLeader waits forRiskUse

Trap: acks=all alone is NOT safe. If the ISR has shrunk to just the leader, "all" means "one". Pair it with min.insync.replicas=2.
The production triple: replication.factor=3 + min.insync.replicas=2 + acks=all.
Tolerates one broker failing with zero loss and zero downtime. Not 3, because then any single restart halts all writes.

unclean.leader.election.enable — if true, a stale non-ISR replica may become leader when all ISR members die: stays available, silently loses records. Default false. Kafka defaults to consistency over availability; this is the switch that flips it. (Literal CAP choice.)

4. Partitioning strategy

Every record is key + value. The key is not metadata — it is the routing decision.

partition = murmur2(serialized_key) % number_of_partitions
CaseBehaviour
Key presentDeterministic hash — same key always → same partition, from any producer, any language. This is what gives ordering.
Key nullSticky partitioner (clients 2.4+): fill a batch for one partition, send, switch. Older clients: strict round-robin per record. "Null key = round-robin" is outdated — it's round-robin per batch.
Explicit partitionOverrides everything; you own rebalancing correctness.
Custom partitionerImplement Partitioner — e.g. VIP tenants to dedicated partitions.
You don't get global ordering. You choose the unit you need ordering within, and make that the key: per-rider, per-account, per-device, per-card.

Failure mode 1 — hot partitions (key skew)

Key by country_code with 60% one country → one partition takes 60% of load; one consumer lags while others idle, and adding consumers cannot help. Choose a high-cardinality, evenly distributed key (user_id good; country/status/event_type bad). For a genuinely hot key: composite key merchant_id:bucket_0..9 — the same salting used for Spark skew.

Failure mode 2 — changing partition count breaks ordering

% number_of_partitions means changing the divisor rehashes every key. A key on p2 under 6 partitions may map to p5 under 10 — old history in p2, new events in p5, so a consumer can read new state before old. Kafka allows this silently, with no warning. Never shrink (impossible), avoid growing keyed topics, over-provision at creation.

Sizing partition count

  • Floor: partitions ≥ peak consumers you will ever want.
  • partitions = target_throughput / per_partition_throughput, plus headroom.
  • Costs: file handles, memory, replication threads, longer leader election. Thousands/broker fine on KRaft; tens of thousands is trouble.
  • Default for a new topic: 2–3× expected consumer count.

Interview line: Partitions buy parallelism and cost global ordering plus per-partition overhead — so size for peak consumers with headroom, because growing later breaks key-ordering guarantees.

Worked example — fraud detection

Rule: "3 transactions in different cities within 10 minutes", per card. Key = credit_card_number (tokenized).

Why transaction_id is the worst possible key: unique per record → every transaction hashes to a different partition. One card's 5 transactions scatter across 5 partitions and 5 consumers. The 10-minute window never sees them together — the rule doesn't fire slowly, it silently never fires.
General rule: keys should be the entity you group by, not the identity of the event.

The key also determines stateful streaming correctness — groupBy(card).window(10 min) only works if all that card's events reach the same task. Re-keying later means a new topic or a repartition step: choosing the key is an architecture decision made once, expensive to reverse.

5. Delivery semantics & exactly-once

GuaranteeMeaning
At-most-onceSend, never retry. Fast, loses data. acks=0.
At-least-onceRetry until acked. No loss, duplicates happen. The default reality.
Exactly-onceNo loss, no duplicates — via the two mechanisms below.

Why duplicates are unavoidable: broker writes the record, its ack is lost in the network, producer times out and retries — the broker has no way to know it's the same record.

Mechanism 1 — idempotent producer

enable.idempotence=true (default since 3.0). Producer gets a PID and stamps each record with a monotonic sequence number per partition. The broker tracks the last sequence per (PID, partition); on retry it recognises the duplicate, drops it, and still returns success. Requires acks=all, retries>0, max.in.flight≤5. Solves duplicates from producer retries — the common case. ~3–5% throughput cost.

Mechanism 2 — transactional API (read-process-write)

Problem: consumer reads topic A, writes topic B, commits its offset. Crash between the write and the offset commit → reprocess → output written twice.

producer.initTransactions();
producer.beginTransaction();
producer.send(outputRecord);
producer.sendOffsetsToTransaction(offsets, groupId);  // offsets INSIDE the txn
producer.commitTransaction();
The offset commit going through the producer is the whole trick — output write and offset commit become one atomic unit. Consumers must set isolation.level=read_committed; the default read_uncommitted sees aborted/open transactions and quietly defeats the design.

The honest limitation

Exactly-once holds only within Kafka. Any external sink (Postgres, S3, Delta, REST) is outside the transaction coordinator's reach. External sinks need their own idempotency: upsert on a natural key, deterministic file naming, or batch-ID dedup (what Delta does — below).

6. Recap — 2D checkpoints + the Delta atomic commit

Re-taught 2026-07-30 because the mechanism underpins every "how do you guarantee exactly-once?" answer.

A micro-batch

Streaming = a loop of small batch jobs: ask the source what's new → freeze that range as batch N → run the query → write to sink → record completion. Batch N is a fixed, named offset range decided before processing — which is what makes replay deterministic.

The checkpoint directory

/checkpoint/
├── offsets/    ← "batch N will read THIS range"  (written BEFORE processing)
├── commits/    ← "batch N finished"              (written AFTER the sink write)
├── metadata    ← the stream's permanent appId
└── state/      ← aggregation/window state (RocksDB)

offsets/47 present but commits/47 absent = crashed mid-batch-47, readable at a glance.

State foundAction on restart
offsets/47 + commits/47start batch 48
offsets/47, no commits/47re-run batch 47 with the exact recorded offset range

The exposure: the crash may have happened after Delta accepted the write but before commits/47 was written. Streaming cannot tell the difference, so it replays. Unprotected, that's duplicates.

The Delta side — SetTransaction

Every Delta write is an atomic commit (a new JSON in _delta_log/, made visible atomically — no half state). A streaming writer adds one extra action:

// _delta_log/00000000000000000012.json
{"add": {"path": "part-0001.parquet", ...}}
{"add": {"path": "part-0002.parquet", ...}}
{"txn": {"appId": "a7f3-stream-id", "version": 47, ...}}
  • appId — which stream (from the checkpoint's metadata); two streams writing one table don't interfere.
  • version — the batch number.

Data files and the claim "stream a7f3 already wrote batch 47" land in the same commit — they cannot disagree.

The two mechanisms meeting

  1. Streaming sees offsets/47 without commits/47 → replays batch 47, same Kafka offsets.
  2. Query recomputes the same rows.
  3. Delta sink scans _delta_log for the latest txn with appId=a7f3 → finds version 47.
  4. 47 is not > 47 → skip the write silently.
  5. commits/47 written, on to batch 48.
Checkpoint = no data loss (every batch processed at least once).
Delta txn = no duplicates (every batch written at most once).
Together = exactly-once. Note the work was redone; the write was not.

What deleting parts of the checkpoint costs

DeletedConsequence
commits/ onlyRecompute wasted, no data impact — Delta's txn dedup still catches the replay because appId survived.
offsets/Loses read position → gap, or re-read from startingOffsets.
metadataNew appId → Delta dedup blind → duplicates. The fatal one.

Rule: the checkpoint is not a cache — it is the stream's identity and its ledger. Deleting it declares a brand-new pipeline. (Proven in the 2D lab: after deletion the rate source re-emitted and duplicates appeared.)
