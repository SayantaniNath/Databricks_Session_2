1. SQL questions (screen + onsite)

Dialect: Presto/Spark SQL — practice in that dialect, not Oracle. Tables are almost always user-event shaped: (user_id, event_time, event_name).

Reported questions

  • Given an events table (user_id, event_time, event_name), compute 7-day retention cohorts by signup date — derive cohorts, join event windows, window-function activity flags. reported 2025
  • Compute Day-N retention for each weekly cohort, given a signup event and an active event.
  • Funnel: what % of Messenger users active yesterday made a video call. Exponent
  • Users who checked out books but didn't return before the due date (per user count). screen
  • Users who checked out books in a category, grouped by age. screen
  • People who checked out a book the same day another person returned it (self-join on dates). screen
  • Sum of total orders + count of distinct customers. screen warm-up
  • Users who called 3+ distinct people in the last week. screen
  • Aggregating transactions by user, with joins across tables. screen, Medium 2025

Generic SQL warm-ups reported (lower signature-value, but real reports)

  • UNION vs UNION ALL — difference + which is faster
  • Top 5 products by sales; % of total sales on first vs last working day of month
  • Second-highest / third-highest salary without TOP/LIMIT; employees without managers; normalize a redundant table

Patterns to drill

  • Retention + cohort analysis (the signature Meta question — multiple stacked CTEs)
  • Funnels with conversion % between steps
  • Full window-function surface: ROW_NUMBER / RANK / DENSE_RANK / NTILE / PERCENT_RANK / CUME_DIST / LAG / LEAD / FIRST_VALUE / LAST_VALUE
  • Self-joins on event tables; date arithmetic; COUNT(DISTINCT ...) traps; CASE-pivots

2. Python questions (screen + onsite)

NOT LeetCode DSA. Practical data manipulation on native structures — lists, dicts, strings, files. Onsite adds streaming patterns.

Reported questions

  • For each string in a list: take the second letter of the first word, return char + count (dict counting). screen
  • Read data.csv, process it, handle file-not-found (try/except — your Python Foundations topic 4). screen
  • Second-highest salary per department from employee records — in pure Python, no SQL. screen
  • Join two lists and sort; remove items from a list by key. screen warm-ups
  • Stream of ride requests → count per 15-minute tumbling window (your 2D watermark/window knowledge, in plain Python). onsite
  • Write a function that dynamically formats a SQL query from input parameters. onsite
  • Given a dict of bookstore locations → list of review strings, dedup reviews per location, then find the most frequent review across all locations. screen, new 2026-07-27
  • Forward-fill: given a list, replace NULLs with the previous non-null value. new 2026-07-27 — DE-relevant pattern
  • Count occurrences of a character in a string; find mismatched words between two strings (case-sensitive). new 2026-07-27
  • Check whether a list of numbers is monotonic (all non-decreasing or all non-increasing). new 2026-07-27
  • Given several lists, compute the average list length. new 2026-07-27

Patterns to drill

  • Dict counting/grouping by hand (defaultdict, Counter)
  • String parsing + list comprehensions; sorting with key=; top-N per group without SQL
  • File I/O + exception handling; generators for large-file processing (your Foundations topics 1–4 — directly relevant)
  • Windowing logic over event streams with plain dicts + timestamps

3. Data modeling (onsite, ~15 min per round — highest-weighted)

Always introduced through a product prompt. Whiteboard a star schema and defend grain, SCD choice, fact type.

Reported prompts

  • Design the star schema for News Feed / Marketplace / Reels — defend grain, SCDs, fact table type. reported repeatedly
  • Ride-sharing platform schema: relationships, PK/FK, how you'd partition transactional tables at scale.
  • E-commerce: products, orders, customers, inventory.
  • Notification system for a Reddit-style app — backend + data model.
  • Movie-theater ticketing system end-to-end.
  • "An Instagram metric is dropping — walk through root-cause analysis, the data model that supports the investigation, and follow-ups."
  • Social media site like Twitter — full schema. new 2026-07-27
  • Track software versions + dependencies. new 2026-07-27
  • Global weather tracking system. new 2026-07-27
  • Video streaming service — scalable schema. new 2026-07-27
  • Multi-tenant application with different access levels. new 2026-07-27
  • ETL pipeline for Uber user engagement — what events to capture, log structure, queryability, metric pre-calculation. Medium 2025 — process note: modeling + ETL are now ONE integrated round, not separate

What they score

  • Clarify ambiguity BEFORE committing; state the grain out loud; additive vs semi-additive vs non-additive facts
  • SCD choices with reasons; bridge tables; conformed dimensions (Kimball vocabulary — your IQVIA/Dow home turf)
  • Partitioning strategy at consumer scale; how the ETL lands the model; adapting when they shift a requirement mid-round

4. Product sense (onsite, ~10 min per round)

  • Define success metrics for an Instagram feature (Reels, Stories, Notifications) — north star + guardrail/counter-metrics
  • Metric X dropped 10% — how do you investigate? (segment, seasonality, logging change, mix shift)
  • Which tables/events must exist to measure this feature? (bridges straight into the modeling section)
  • How would you improve Facebook search? new 2026-07-27
  • What metrics would you examine to grow engagement on Instagram Stories? new 2026-07-27
  • Design a feature to increase Marketplace transactions. new 2026-07-27
  • How would you use data to decide on a new WhatsApp feature? new 2026-07-27
  • Propose how to measure success of a new video-recommendation algorithm. new 2026-07-27
  • Housing marketplace feature — how would you measure success? Medium 2025, onsite round 1

Framework: user action → north star metric → counter-metrics → grain of the fact table that measures it. Your schema-derivation recipe from the SD ledger pattern applies directly.

5. Ownership / behavioral (30 min, with a manager)

  • Led a project end-to-end
  • Disagreed with manager/lead — how resolved
  • Process improved with measurable business impact
  • Learned a new tool/system fast and delivered
  • Went the extra mile for a project. new 2026-07-27
  • Biggest anticipated challenge in the DE role. new 2026-07-27
  • Made a quick decision without all the necessary information. new 2026-07-27 — matches Pillar 8's "decision with incomplete info"

Run by a Data Engineering manager, not a peer — first-hand account confirms situational/scenario-style follow-ups, not pure SAR recitation.

Your four stories: Citi consumption layer (ownership+tradeoff, Q2), Playwright ElementHandle (rigor, Q4), IQVIA DV2-over-Kimball (decision under volatility), mentoring 3 juniors (level). Under 5 min each, numbers included, "I" not "we".
