Quick-reference: OLTP Fundamentals

Normalization (1NF → 3NF)

FormRule
1NFEvery column holds a single atomic value — no lists/repeating groups in one cell
2NF1NF + every non-key column depends on the whole composite key (kills partial dependencies)
3NF2NF + no non-key column depends on another non-key column (kills transitive dependencies)

Junction tables are driven by cardinality, not normal form. Many-to-many relationships always need a junction table (e.g. Orders↔Products via OrderLineItems); one-to-many just needs a foreign key on the "many" side.

ER Diagram Notation (crow's foot)

Order ||──o< OrderLineItems >o──|| Product
  • | = "exactly one"    o = "zero/optional"    < = crow's foot = "many"
  • One many-end = one-to-many (plain FK). Two many-ends = many-to-many (junction table needed).

Derivable (Redundant) Relationships

A relationship implied by composing two other relationships (e.g. Customer↔Product via Customer→Order→OrderLineItems→Product) should not get its own table — it's answerable via JOINs across existing FKs. Only give something its own relationship/table if it captures a fact not implied by the existing path (e.g. a Favorites table is genuinely separate from purchase history).

Keys & FK Delete Behavior

ClauseBehavior
ON DELETE RESTRICT (default)Blocks the delete, errors out
ON DELETE CASCADEDeletes child rows automatically
ON DELETE SET NULLOrphans child rows (FK → NULL)
ON DELETE SET DEFAULTSets FK to a predefined default

Same options exist for ON UPDATE. Degenerate dimension: an ID with no useful descriptive attributes (e.g. order_id) lives directly on the fact table — no separate dimension table needed.

Kimball Dimensional Modeling — Core Framework

Step 1: Always declare grain first

Grain = what one row of the fact table represents. State it out loud before building anything else — everything downstream (dimensions, fact type, SCD) depends on this answer.

Three fact table types

TypeShapeAdditivityExample
TransactionOne row per discrete event; same action can repeat unboundedly, any orderFully additiveReels engagement (like/comment/share/view)
Accumulating snapshotOne row per process instance; entity moves through a small fixed set of stages once each; same row updated as it progressesFully additiveRide lifecycle (requested→accepted→completed); checkout funnel; notification lifecycle (created→delivered→opened)
Periodic snapshotOne row per entity per fixed time interval, repeated indefinitely (no "end")Semi-additive (sum across entities OK, never across time)Daily inventory level; daily account balance

The distinguishing test: does the entity repeat the same action arbitrarily many times in any order (transaction), move through a small fixed sequence exactly once (accumulating snapshot), or represent an ongoing state sampled at intervals with no defined end (periodic snapshot)?

Dimension patterns

  • Degenerate dimension — an identifier with no descriptive attributes worth a lookup table (e.g. order_id); lives directly on the fact row.
  • Role-playing dimension — the same dimension table referenced multiple times in one fact row for different roles (e.g. DimLocation referenced as both pickup_location_id and dropoff_location_id; DimDate referenced as order_date/ship_date/delivery_date).
  • Conformed dimension — the same dimension (same keys, same meaning) shared across multiple fact tables from different business processes (e.g. DimProduct shared by FactSales and FactInventory), enabling drill-across queries (e.g. inventory turnover = units sold ÷ avg inventory, joined through the shared dimension).
  • Bus matrix — documents which conformed dimensions each fact table (business process) uses:
    DimProductDimDateDimCustomer
    FactSales✅✅✅
    FactInventory✅✅—
  • Polymorphic association problem — a single FK column can't reference different target tables depending on the row (e.g. a notification's source could be a post, comment, or message). Three resolutions:
    1. Separate nullable FK columns per possible target (sparse but keeps real FK constraints)
    2. (source_type, source_id) pair — no DB-level FK, integrity enforced in app code
    3. Unified bridge dimension (e.g. DimSource) — an ETL step unions all source types into one lookup table with a type discriminator; fact table gets one clean FK. Costs an extra sync step, but restores real FK integrity and clean queries.

Star vs. Snowflake Schema

Star (denormalized)Snowflake (normalized)
Dimension attributes inlined directly (e.g. movie genre repeated on every showtime row)Dimension references other dimensions via FK (e.g. DimShowtime → DimMovie)
Fewer joins, simpler for BI/reportingSingle point of update, less redundancy
Default choice — dimension tables are tiny vs. fact tables, so redundancy cost is negligibleOnly worth it for very large/deep-hierarchy dimensions, or attributes needing single-point-of-truth updates

SCD Types

TypeBehaviorLimitation
Type 1Overwrite in placeDestroys history — retroactively contaminates past analysis
Type 2New row per change, with effective_date/end_dateNone for history; costs storage growth + point-in-time join complexity
Type 3Add a "previous value" columnOnly tracks ONE prior value — can't represent multiple transitions

Staff-level layer: don't just pick Type 2 silently — name the trade-off (storage growth, point-in-time join cost at scale) and flag the retention-window decision (unlimited history vs. capped/archived) explicitly to the team.

SCD Type 2 with Delta MERGE INTO — the merge_key trick

A single MERGE INTO can only take one action (UPDATE or INSERT) per matched key, but Type 2 needs both: expire the old row AND insert a new one. The fix — union the update set with a duplicate copy whose merge key is forced to NULL, guaranteeing those rows fall into the INSERT branch:

MERGE INTO DimUser t
USING (
    SELECT u.customer_id AS merge_key, u.*
    FROM updates u

    UNION ALL

    SELECT NULL AS merge_key, u.*
    FROM updates u
    JOIN DimUser t ON u.customer_id = t.customer_id
    WHERE t.is_current = true AND u.account_type <> t.account_type
) staged
ON t.customer_id = staged.merge_key
WHEN MATCHED AND t.is_current = true AND t.account_type <> staged.account_type THEN
    UPDATE SET is_current = false, end_date = staged.effective_date
WHEN NOT MATCHED THEN
    INSERT (customer_id, account_type, is_current, effective_date, end_date)
    VALUES (staged.customer_id, staged.account_type, true, staged.effective_date, NULL)

One atomic transaction — no risk of a partial expire-without-insert if the job fails halfway. Not yet run hands-on against a real Delta table — still open.

The 6 Live Mock Rounds

Round 1 — Reels Engagement reported repeatedly

"Track engagement on Reels — likes, comments, shares, views, watch-time. Support real-time dashboards + historical analytics."

  • Grain: one row per engagement event (not a daily rollup — pre-aggregating destroys sub-day resolution needed for real-time)
  • Fact type: transaction fact table — engagement_count=1 and watch_duration_seconds, both fully additive
  • Dimensions: DimUser, DimMedia, DimDate, DimActionType
  • SCD: Type 2 for DimUser.account_type (personal→business) — correctly reasoned and defended against Type 1/3

Round 2 — Ride-Sharing Platform

"Riders request rides, drivers accept/complete. Support live operational app + analytics (trip volume, driver earnings, surge effectiveness)."

  • Fact split: FactDriverLocation (per-second GPS pings — a time-series stream, not a warehouse fact table) separated from FactTrip (the real Kimball fact) — correctly reasoned from frequency mismatch alone
  • Grain/fact type: initially guessed transaction (pattern-matched to Round 1); self-corrected to accumulating snapshot once compared against the checkout-funnel pattern
  • Partitioning at scale: date (primary) + region/geography (secondary) — solves both time-bounded query efficiency and cross-region hotspot risk
  • Dimensions: DimRider, DimDriver, DimDate, DimLocation (role-playing: pickup + dropoff)

Watch: grain classification defaulted to pattern-matching the previous round rather than re-deriving from scratch — worth a cold redo.

Round 3 — E-Commerce

"Products, orders, customers, inventory. Analyze sales trends, inventory turnover, customer lifetime value."

  • Fact tables: FactSales + FactInventory — correctly rejected a third table (FactCustomerValue) using the derivable-relationship principle (CLV is a rollup of FactSales, not its own grain)
  • FactInventory: initially guessed accumulating snapshot; self-corrected to periodic snapshot (grain: product+date, quantity_on_hand semi-additive)
  • Dimensions: DimProduct, DimDate, DimCustomer (Sales only) — order_id correctly named as degenerate dimension
  • Conformed dimensions: DimProduct + DimDate shared across both facts, enabling the inventory-turnover drill-across query; bus matrix concept landed

Round 4 — Instagram Metric-Drop Investigation reported

"An Instagram metric is dropping — walk through root-cause investigation, the data model that supports it, and follow-ups."

  • Product sense: correctly led with "what kind of metric," then correctly picked the 3 substantive clarifying questions (segment/platform split, logging-change check, seasonality) out of 4 options, rejecting a decoy
  • Reveal: Android-specific real drop in Reels watch-time, no logging change, not seasonal
  • Schema gap: correctly identified Round 1's FactReelsEngagement was missing DimDeviceOS/platform — added it without rebuilding the rest (the "adapt mid-round" skill Meta explicitly grades)
  • Follow-up: proposed video/codec compatibility on Android as next investigation step

Strongest round of the day — full loop completed with only light nudging.

Round 5 — Notification System (Reddit-style)

"Users get notified about replies, upvotes, mentions, DMs. Support real-time display + engagement analytics (open rates, which types drive re-engagement)."

  • Fact table: single FactNotification; initially guessed transaction, self-corrected to accumulating snapshot (created→delivered→opened, fixed lifecycle once per notification)
  • Polymorphic problem: notification source can be post/comment/message — no single FK target. Independently proposed the unified DimSource bridge dimension resolution after the concept was taught
  • Correctly worked out when the same domain needs a periodic snapshot instead (unread-notification-backlog tracking) — good sign of generalizing the framework
  • Dimensions: DimUser, DimDate, DimNotificationType, DimSource

Round 6 — Movie-Theater Ticketing

"Customers book seats for showtimes; showtimes belong to movies at theaters/screens. Support live booking (seat availability) + analytics (revenue, utilization, popular showtimes)."

  • Correctly identified live seat-booking as an operational/event-stream concern, separate from the Kimball analytical model (parallel to GPS-location reasoning)
  • Repeated miss: proposed FactRevenue → FactShowtime → FactPrice in sequence before landing on the correct FactTicketSale (one row per seat booked). Each guess named the table after a derived measure or a scheduling entity instead of the underlying transactional event/verb.
  • Correctly reasoned DimSeat deserves a full dimension (not degenerate) by applying the test against the stated "theater utilization" goal
  • Correctly chose star over snowflake for DimShowtime/DimMovie with standard Kimball reasoning

Data Lake vs. Data Warehouse / ETL vs. ELT added 2026-07-27

Data Lake vs. Data Warehouse

Data LakeData Warehouse
Data shapeRaw, any format (structured/semi/unstructured)Structured, curated, modeled (facts/dims)
SchemaSchema-on-read — flexible, decided at query timeSchema-on-write — enforced before it lands
StorageCheap object storage (S3, ADLS)Pricier, optimized for fast SQL
Best forML, exploratory analysis, streaming, variety/volumeBI dashboards, governed reporting, fast structured queries

ETL vs. ELT — the difference is WHERE transformation happens relative to load

  • ETL (Extract → Transform → Load): shaped in separate compute (Glue/Spark/ETL tool) before landing. Use when: strict governance requires validated data before it lands, or transformation needs dedicated compute separate from the warehouse.
  • ELT (Extract → Load → Transform): raw lands first, transform happens after, using the target's own compute. Use when: fast ingestion + flexibility to decide transform logic later; modern elastic-compute warehouses (Snowflake/BigQuery/Databricks). dbt is the classic ELT tool — only ever transforms data already loaded, via SQL models (4D in the plan).

30-second spoken answer, grounded in ClinicalFlow: "ClinicalFlow lands raw Synthea data in S3 first, encrypted, before any transformation touches it. From there it moves through a medallion pattern — raw → silver → gold — where transformation happens after landing, using Glue and EMR as the compute layer. So even though I named the Glue job an 'ETL job,' the architecture is really ELT: extract and load raw first, transform in place. I chose that over a classic pre-load ETL pipeline because in a lakehouse you want the raw layer preserved — for reprocessing if a transformation rule changes later, and for audit lineage, which matters a lot in a HIPAA context."

If pushed on the compliance angle (raw briefly holds PHI before de-id): "That's a deliberate trade-off, not a gap — the raw zone is SSE-KMS encrypted, access-restricted via IAM, every access logged via CloudTrail. De-identifying before anything lands would remove the raw copy entirely, which sounds safer but kills your ability to audit or reprocess if the de-id logic itself needs to change later. I chose auditable-and-controlled over unrecoverable."

Staff-level layer, if asked "why not just do ETL": "ETL made sense when warehouse compute was expensive and you had to shape data before it landed. Now that Spark/EMR compute is elastic and cheap relative to storage, ELT lets you defer transformation decisions instead of locking into one schema the moment data arrives. The cost is you need real governance on the raw zone itself, not just the curated output — which is exactly what the KMS encryption, IAM restrictions, and CloudTrail logging are doing here."

Priority Fix Before the Real Screen

Fact-table naming — the single clearest, most fixable gap from all 6 rounds. Missed 3x in a row in Round 6 alone. Rule to drill: name the fact table after the business event/verb happening (e.g. "a ticket gets sold," "a trip happens"), never after a derived measure (FactRevenue, FactPrice) or a scheduling/descriptive entity (FactShowtime). Quick drill: given a fresh prompt, say the fact table name FIRST, before anything else, and justify it as an event.
