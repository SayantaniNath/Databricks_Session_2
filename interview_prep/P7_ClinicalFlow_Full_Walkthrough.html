AWS ClinicalFlow — Full Walkthrough & Interview Defence

Rebuilt 2026-08-07 from the actual repo (~/aws-healthcare-datalake, 17 commits, 4 PRs) and the live infra notes — not from memory. Every number below is real.

The framing rule, every time. This is a personal portfolio project. Say so unprompted. Real figures: 64,338 synthetic patients, 10 years, 8.2 GB across 16 CSVs. Never "100K patients" and never "50M records" — those were the original target, never reached, and the 50M figure is still wrong on the master resume PDF and needs fixing. The honest number is more than good enough; the inflated one dies on the first follow-up.

0. The pitch — three lengths

30 seconds: "ClinicalFlow is a healthcare lakehouse I built end to end on AWS. Synthetic EHR data from Synthea — about 64,000 patients over ten years — lands in an encrypted S3 lake, gets de-identified to HIPAA Safe Harbor standard in Glue, validated, written to an Iceberg silver layer, and aggregated on EMR Serverless into a 30-day readmission analysis with statistical anomaly detection. Governance runs through Lake Formation column grants, GDPR erasure through a consent dimension, and audit through CloudTrail."
2 minutes — add the decisions: "The interesting part wasn't the pipeline, it was the compliance design. Safe Harbor requires removing eighteen identifier classes, so the silver layer drops twelve columns outright, tokenises the patient ID to a fresh UUID, truncates ZIP to three digits and buckets birthdate into five-year ranges. That created the problem I found most instructive: once IDs are tokenised, silver cannot join back to encounters — which is the point of de-identification, but it broke my aggregation job and produced zero rows. I fixed it by running the analytical join on the raw layer inside the controlled environment, and noted that in production you'd either tokenise every table consistently or keep a secure re-identification mapping under separate access control. That trade-off — analytical utility versus de-identification — is the real design question in healthcare data."

2. Step by step — what was done, and why

Step 1 — Data generation

Synthea, Massachusetts, seed 42 (reproducibility), 10 years, 64,338 patients → 16 CSVs, 8.2 GB. Largest: claims.csv 2.1 GB, procedures.csv 1.8 GB, imaging_studies.csv 1.7 GB, encounters.csv 1.0 GB, patients.csv 18 MB.

Why synthetic: real EHR data requires credentialing (MIMIC/PhysioNet) and cannot go in a public GitHub repo. Synthea is statistically realistic, clinically coherent, and licence-clean.

Step 2 — Encryption and bucket hardening (before any data landed)

  • KMS customer-managed key alias/clinicalflow-cmk — CMK not SSE-S3, because a CMK gives you your own key policy, rotation control, and — critically for HIPAA — every key use is logged in CloudTrail.
  • S3 clinicalflow-datalake-941141114246: block-all-public-access ON, versioning ON, default SSE-KMS.
  • CloudTrail clinicalflow-audit-trail, itself KMS-encrypted, with S3 data events enabled on the bucket — management events alone would not capture object-level reads, which is what an auditor asks for.
Order matters and is worth saying: encryption and audit were configured before the first upload. Retro-fitting encryption leaves unencrypted object versions behind — and with versioning on, they persist.

Step 3 — Catalog the raw layer

Glue Crawler → clinicalflow_raw, 17 tables. Schema-on-read: no transformation, raw stays immutable as the audit baseline.

Step 4 — HIPAA Safe Harbor de-identification (the core)

glue_jobs/hipaa_deid_patients.py. Four transformation classes:

ActionColumnsSafe Harbor rationale
Dropped (12)first, middle, last, maiden, ssn, passport, drivers, prefix, suffix, address, lat, lonDirect identifiers § 164.514(b)(2). maiden is still a name; drivers is a government ID; lat/lon is geography below county level.
Tokenisedid → fresh uuid4()Breaks linkability to the source record
Truncatedzip → first 3 charsSafe Harbor geographic rule (and 3-digit zones under 20,000 people must go to 000)
Generalisedbirthdate → birth_year_bucket, 5-yearAll individual dates must go; (year/5)::int * 5
DroppeddeathdateIndividual-related date

Result: 15 clean columns.

The quarantine pattern

3 rows in patients.csv (lines 60385, 60401, 64324) had two records concatenated onto one line — a Synthea output bug. Glue read them as over-wide rows and auto-named the spill columns col28…col35. Clean rows have those as NULL.

overflow_cols = [c for c in patients.columns if c.startswith('col')]
is_malformed  = reduce(lambda a, b: a | b,
                       [F.col(c).isNotNull() for c in overflow_cols])

quarantine_df = patients.filter(is_malformed)
clean_df      = patients.filter(~is_malformed)

Quarantined rows are written to quarantine/patients/ in append mode with quarantine_reason and quarantine_ts.

Why append, not overwrite — and this is the answer an interviewer wants: the quarantine is the audit trail. If the source is corrected and reprocessed, the original bad rows must still be on record. Overwrite would destroy the evidence that you ever rejected anything. 64,338 − 3 = 64,335 rows in silver, and being able to account for exactly three missing records is the point.

resolveChoice

Those malformed rows also spilled text into numeric columns, so Glue inferred ambiguous union types ({'double': 41009.33, 'string': None}). Forced to concrete types:

.resolveChoice(specs=[("zip","cast:string"), ("healthcare_expenses","cast:double"),
                      ("healthcare_coverage","cast:double"), ("income","cast:long"),
                      ("fips","cast:long")])

zip is deliberately a string — "02134" loses its leading zero as a number.

Step 5 — Two independent validation layers

Great ExpectationsGlue DQDL
Scope17 checks, 17/17 pass8 rules, 8/8 pass
ReadsThe actual dataThe Glue Catalog schema, not S3 files directly
Checksnot-null, row-count range, regex, value lengthsColumnCount, UUID-format regex, PHI-absence audit

Why both: GE proves the data is right; DQDL proves no PHI column has crept back into the schema. They fail for different reasons — a schema regression passes GE and fails DQDL.

Step 6 — Iceberg silver

Rewritten as Iceberg v2 registered in the Glue Catalog, then GE re-run (17/17) against the Iceberg table to prove the format migration was lossless.

--datalake-formats iceberg
--conf spark.sql.catalog.glue_catalog=org.apache.iceberg.spark.SparkCatalog
 --conf spark.sql.catalog.glue_catalog.catalog-impl=org.apache.iceberg.aws.glue.GlueCatalog

Step 7 — GDPR consent dimension

dim_patient_consent (Iceberg v2, 128 MB target file size): consent_given, consent_date, erasure_requested (~5% simulated), erasure_date, last_updated.

Why a separate dimension rather than a flag on patients: consent changes on a completely different cadence to demographics, it has its own audit and retention requirements, and erasure must be actioned without rewriting the patient record itself. Also the honest architectural point — GDPR erasure and Iceberg immutability are in tension: you satisfy erasure with row-level deletes plus snapshot expiry, and you must ensure retained snapshots don't silently preserve erased data.

Step 8 — EMR Serverless: readmission aggregation

emr_jobs/readmission_aggregation.py: 30-day readmission flag via LAG over PATIENT ordered by START, then aggregation by demographic group.

w = Window.partitionBy("PATIENT").orderBy("START")
.withColumn("prev_stop", F.lag("STOP").over(w))
.withColumn("days_since_last", F.datediff(F.col("START"), F.col("prev_stop")))
.withColumn("is_readmission", F.when(F.col("days_since_last") <= 30, 1).otherwise(0))
...
.groupBy("GENDER","RACE","ETHNICITY","STATE","birth_year_bucket")
.agg(F.count("encounter_id").alias("total_encounters"),
     F.sum("is_readmission").alias("readmissions_30d"))
.withColumn("readmission_rate", F.round(readmissions_30d/total_encounters*100, 2))

Timestamps parsed with try_cast — returns NULL instead of failing the job on a bad value.

Step 9 — Anomaly detection in pure Spark SQL

(readmission_rate - AVG(readmission_rate) OVER ())
  / NULLIF(STDDEV(readmission_rate) OVER (), 0)   AS z_score
ABS(...) > 2.0                                    AS is_anomaly

NULLIF(stddev, 0) guards division by zero when every group has the same rate.

Step 10 — Gold serving with column-level access control

Athena views governed by Lake Formation column grants:

  • vw_patient_demographics → analyst role: id, gender, race, ethnicity, state, zip, birth_year_bucket
  • vw_patient_financials → finance role: id, income, healthcare_expenses, healthcare_coverage

The enforcement point: analyst IAM users hold zero direct S3 or Glue permissions. All access flows through Lake Formation grants — otherwise a view is theatre, because the analyst could read the underlying S3 objects directly.

3. Why this, not that

DecisionAlternativesDefence
Safe HarborExpert DeterminationSafe Harbor is a deterministic checklist of 18 identifier classes — implementable and testable in code. Expert Determination needs a qualified statistician certifying re-identification risk; more analytically useful (you can keep dates), but not something a pipeline can assert on its own.
Tokenise ID (random UUID)Hash, encrypt, dropA hash of a known ID space is reversible by brute force — a rainbow table over 64K IDs is trivial. Encryption is reversible by design, so the data stays PHI. Dropping loses row identity entirely. Random UUID is genuinely one-way — and that's exactly what broke the join, which is the honest cost.
Glue for de-id, EMR for analyticsEverything in one engineGlue: serverless, catalog-integrated, DynamicFrame's resolveChoice handles the messy schema — right for ingest. EMR Serverless: full Spark control and cheaper for heavy compute, no cluster to manage — right for the window-function aggregation. Different tools for different failure modes.
IcebergDelta, Hudi, plain ParquetOpen format, engine-neutral (Athena, EMR, Spark, Trino all read it), and first-class in AWS. Plain Parquet gives no ACID, no time travel, no schema evolution. Delta is stronger inside Databricks; this is an AWS-native stack. Hudi wins on very heavy upsert workloads, which this isn't.
Athena + Lake FormationRedshift (planned, then dropped)Own the pivot — it's a better answer than the original plan. The branch is literally named feat/redshift-gold, but what shipped was Athena views + Lake Formation grants. Say it as a decision: "I'd planned a Redshift gold layer, then realised there was no high-concurrency BI workload to justify a cluster idling at cost. Athena queries the lake in place and Lake Formation gives column-level grants centrally, which was the actual requirement." Redshift wins for sub-second high-concurrency BI — that workload didn't exist here.
Z-score, not MLIsolationForest / clusteringStarted with IsolationForest — sklearn isn't available on EMR Serverless. Rewrote as z-score in Spark SQL. Honestly: for a single-metric outlier check on a few hundred groups, z-score is the right answer anyway — explainable to a clinician, no training, no model to maintain. ML would be justified with multivariate signals.
CMK, not SSE-S3SSE-S3Own key policy, own rotation, and every decrypt is CloudTrail-logged. For PHI the audit trail is the requirement.

4. The bugs — rehearse these, they are the most valuable part

Interviewers learn more from what broke than from what worked. Each of these has a clean cause → fix → lesson shape.

Bug 1 — Aggregation returned 0 rows

Cause: joined silver (tokenised UUIDs) to encounters.PATIENT (original Synthea IDs). Zero matches — silently, because an inner join on no matches is empty, not an error.
Fix: read raw patients.csv for the join, inside the controlled environment.
Lesson: de-identification deliberately destroys join keys. In production: tokenise every table with a consistent mapping, or hold a secure original→token table under separate access control. This is the single best story in the project — a compliance control colliding with analytical need.

Bug 2 — sklearn not on EMR Serverless

Rewrote IsolationForest as a Spark SQL z-score. Lesson: know your runtime's libraries before designing around them; and check whether the simpler statistical method was sufficient all along — here it was.

Bug 3 — Union struct types from 3 malformed rows

Three bad lines out of 64,338 corrupted the inferred schema for the entire table. Fixed with resolveChoice + quarantine. Lesson: schema inference is only as good as the worst row in the file.

Bug 4 — Spurious partition_0 from the crawler

The crawler inferred a partition column that didn't exist, breaking the DQDL ColumnCount rule. Fixed by dropping the table and recreating it via CLI without partition keys. Lesson: DQDL evaluates the Glue Catalog schema, not the S3 files — catalog drift is its own failure class.

Bug 5 — Iceberg catalog config, three attempts

  1. Multiple --conf keys in the Glue console silently collapse to the last one (it's a dict) — chain them into a single value.
  2. spark.conf.set() after the SparkContext starts is too late for catalog plugin registration — it must be a job parameter.
  3. GlueCatalog does not implement Spark's CatalogPlugin — you need SparkCatalog with catalog-impl=GlueCatalog.

Plus: an existing Parquet table blocks createOrReplace() for Iceberg — drop it first.

5. Edge cases an HM will probe

Q: Is Safe Harbor de-identification actually sufficient?

It's the legal standard, not a guarantee. Known residual risk: quasi-identifier re-identification — gender + race + ethnicity + 3-digit ZIP + 5-year birth bucket can be unique for rare combinations in a small population. Safe Harbor doesn't require k-anonymity. In production I'd measure the smallest equivalence-class size and suppress or further generalise groups below a threshold (k=5 or k=11 is common). Volunteering this is a strong signal.

Q: What happens when a patient requests erasure?

Set erasure_requested in dim_patient_consent, then delete the rows from the Iceberg table — and expire the snapshots, otherwise time travel still holds the data and you haven't complied. The tension: Iceberg's immutable snapshots are excellent for audit and directly at odds with the right to be forgotten. You resolve it with a snapshot-retention policy short enough to satisfy erasure SLAs but long enough for audit — and you write that policy down.

Q: How does this handle late-arriving or corrected records?

Currently it doesn't — it's a full-refresh overwrite. That's honest and it's the right next change: Iceberg MERGE INTO keyed on the business key, with SCD Type 2 on the patient dimension so corrections version rather than overwrite history.

Q: What if the source schema changes?

The crawler would pick up a new column and DQDL's ColumnCount would fail — which is the desired behaviour, a loud stop rather than silent PHI leakage. The gap: a renamed PHI column would pass the drop list, since it drops by name. Production fix: tag-based classification, or an allow-list (only these 15 columns may reach silver) rather than a deny-list. Deny-lists fail open; allow-lists fail closed — and for PHI you want fail-closed.

Q: Is this idempotent? Can you re-run it safely?

Mostly. Silver is overwrite, so re-running is deterministic — except the UUID tokenisation, which generates fresh IDs every run, so silver IDs are not stable across runs. Fine for a de-identified snapshot; wrong if anything downstream persists those IDs. Production fix: a deterministic keyed token (HMAC with a secret) or a persisted mapping table. Quarantine is append, so it's cumulative by design.

Q: How would you scale this to 200× the data?

Partition raw by ingest date and silver by birth_year_bucket or state; move from full refresh to incremental MERGE; size EMR Serverless by measured shuffle rather than guesswork; Iceberg compaction and sorted file layout for the analytical predicates; and watch the small-files problem, which is what actually bites first at scale.

Q: What's the cost, and how would you control it?

Built for well under $100 by keeping EMR and any orchestration ephemeral — spin up, run, tear down. Levers: S3 lifecycle to Glacier for raw beyond the retention window, Iceberg compaction to cut request costs, right-sized EMR workers, Athena's scanned-bytes charge managed with partitioning and columnar formats.

Q: Where's the orchestration?

Phase 1 was run step by step deliberately, to see each failure clearly. Phase 2 is MWAA with the DAG developed locally first and the environment torn down after the demo — MWAA has a real hourly cost. Honest current state: not yet built.

6. What is genuinely not done — say these before you're asked

  • Only the patients table is de-identified. Encounters, claims, procedures and the rest remain raw. A complete implementation would apply the same treatment consistently across every table.
  • No orchestration — Phase 2 (MWAA).
  • No streaming — Phase 3 (Kinesis → Lambda → Firehose → S3).
  • No incremental/CDC — full refresh only.
  • No k-anonymity measurement.
  • ❌ NO REDSHIFT. Ever.
